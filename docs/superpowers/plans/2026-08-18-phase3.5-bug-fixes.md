## Global Constraints

Copied from `docs/PHASE4-CARRYOVER.md`'s "Decisions Phase 2 made that Phase 4 should not silently reverse". These bind every task in this plan.

- **`org_id` must never appear in application code.** It is filled by the column default `private.current_org_id()`, and RLS is the only read filter. Passing it explicitly is a bug even when it produces the right answer.
- **Nothing may `grant usage on schema private`.** Policy expressions store a parse tree holding the function's OID, so only `EXECUTE` is checked; a plpgsql body resolves names at runtime and would need schema `USAGE`. That asymmetry is deliberate.
- **The `service_role` key must never appear in a `NEXT_PUBLIC_` variable or in application code.** It lives only in `.env.test.local`, which is gitignored.
- **The storage seam throws; it does not return `false`.** `tsc` cannot catch a regression here — `if (!save(x))` on a promise is never true — so convert callers by hand.
- **`createInvoice` stays separate from `saveInvoice`.** Do not dispatch internally.
- **Creating an invoice is not optimistic.** The server allocates the number.
- **Unit tests drive `src/test/fake-seam.ts`, not MSW.** `src/test/fake-seam.test.ts` asserts the fake exports exactly what `src/lib/storage.ts` does — when the seam gains an export, the fake gains it too, or every test that mocks storage starts calling `undefined`.
- **Inline `eslint-disable` comments are not used in this repo.** Suppressions go in `eslint.config.mjs`'s `files:` list — see that file's own comment.
- **Temporary files go in the session scratchpad directory**, never `/tmp` and never the repo.

## Process note — read before writing any test

Seven tests in this project have passed for the wrong reason, via three distinct mechanisms:

1. A `waitFor` whose condition holds during loading as well as after failure.
2. A mutation that breaks two assertions, so the run dies on the first and never proves the second, load-bearing one.
3. An assertion that holds identically in the broken and working states — "the button is absent" passes whether the gate is correct or permanently closed.

**Falsifying a test is not sufficient on its own.** After breaking the implementation, check that *the number of tests that failed matches the number that should have failed*. A probe reporting three failures where six tests depend on the behaviour is the tell.

And: **"all pre-existing tests pass unmodified" does not prove a refactor was faithful.** It proves no *tested* behaviour changed.

## Task 1: Invoice-number conflicts are per brand, not global

Closes: `docs/PHASE4-CARRYOVER.md` — "Invoice-number conflict detection is global, not per-brand."

**Why this is first, and why it is the most serious item on the list.** `invoices_number_unique` is `unique (org_id, brand_id, invoice_number)` — see `supabase/migrations/20260811183756_same_org_invoice_refs.sql:57`. Numbering is per brand, so two brands sharing an `invoicePrefix` may legitimately both hold `INV-2026-001`, and the database will never reject that. Both import paths nevertheless match on the invoice number alone. Three consequences, the second of which is data loss:

1. The file importer shows a conflict dialog for a pair that does not conflict.
2. Choosing **Overwrite** runs `saveInvoice({ ...incoming, id: match.id })` — writing brand A's incoming invoice over **brand B's** existing one.
3. `new Map(...)` keeps the last entry for a duplicated key, so which brand's invoice gets clobbered is arbitrary.

- Modify: `src/components/invoices/import-export.tsx:178-190`
- Test: `src/lib/import-pipeline.test.ts`
- Test: `src/components/invoices/import-export.test.tsx`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: `export function conflictKey(invoice: Invoice): string` from `@/lib/import-pipeline`. Nothing else uses it. It is exported solely so the detection site and the write site cannot drift apart.

## Task 2: `saveBrand` tells the caller what actually persisted

Closes: `docs/PHASE4-CARRYOVER.md` — "`saveBrand` is not atomic."

**The defect.** `saveBrand` upserts the row, uploads the object, then writes the path back — in that order, because the bucket's INSERT policy requires the row to exist and the id is generated client-side. A failure in the second half rejects the promise while the row — including every unrelated field edited in the same save — is already committed. `brand-form.tsx` catches that rejection and toasts "Couldn't save this brand — try again", which is false about everything except the logo, and sends the user back to a form whose contents are already stored.

This task does **not** make `saveBrand` atomic. It cannot be: the ordering is forced by the policy. It makes the failure *legible*, so callers stop reporting it as a total failure.

- [ ] **Step 3: Add `LogoUploadError` and throw it from `saveBrand`**

In `src/lib/storage.ts`, above `saveBrand`:

```ts
/**
 * The brand row committed; its logo did not.
 *
 * `saveBrand` writes the row before it uploads, because the bucket's INSERT
 * policy needs the row to exist and a brand's id is minted client-side. A
 * failure in the upload half therefore cannot roll the first half back, and
 * a caller that reads a plain rejection as "nothing changed" is wrong about
 * every field except the logo.
 *
 * `brand` is what is actually in the database now — including the base64
 * still sitting in `logo_data`, which is what the brand renders from until
 * the next successful save re-attempts the upload.
 */
export class LogoUploadError extends Error {
  constructor(
    readonly brand: Brand,
    override readonly cause: unknown
  ) {
    super("Saved, but the logo could not be uploaded");
    this.name = "LogoUploadError";
  }
}
```

Then wrap the upload half of `saveBrand`:

```ts

        .eq("id", result.id)
        .select("*")

      // `result` is the row the first write already committed. Rethrowing
      // bare would lose that fact — see the class comment.
      throw new LogoUploadError(result, err);
    }

```

```ts
 * service-role key must never be reachable from application code.

function required(name: string): string {
  const value = process.env[name];
  // Empty-string, not just undefined: a shell exporting an unset variable

  if (!value) {
```

```sql
-- sentences for names, where every policy in 20260811141631_rls_policies.sql
-- is `<table>_<verb>`. Postgres has no ALTER POLICY ... RENAME that also

-- The text comparison below is deliberate and must survive the rename:
-- `::uuid` RAISES 22P02 on a non-uuid path segment rather than returning
-- false, and `and` has no guaranteed evaluation order — a policy that throws
-- turns a permission check into a 500. See the original migration's comments
-- for the full reasoning.

drop policy "brand logos are readable by their brand's org" on storage.objects;
drop policy "brand logos are writable by their brand's org" on storage.objects;
drop policy "brand logos are replaceable by their brand's org" on storage.objects;

create policy brand_logos_select
  on storage.objects for select to authenticated
  using (
    bucket_id = 'brand-logos'
    and exists (
      select 1 from public.brands b
      where b.id::text = (storage.foldername(objects.name))[1]
    )
  );

create policy brand_logos_insert
  on storage.objects for insert to authenticated
  with check (
    bucket_id = 'brand-logos'
    and exists (
      select 1 from public.brands b
      where b.id::text = (storage.foldername(objects.name))[1]
    )
  );

-- Both `using` and `with check`, unchanged from the original: `using` picks
-- the row to update, `with check` validates the result. Upsert needs UPDATE
-- as well as INSERT, because `upload(..., { upsert: true })` issues an
-- `INSERT ... ON CONFLICT DO UPDATE` under the hood.
create policy brand_logos_update
  on storage.objects for update to authenticated
  using (
    bucket_id = 'brand-logos'
    and exists (
      select 1 from public.brands b
      where b.id::text = (storage.foldername(objects.name))[1]
    )
  )
  with check (
    bucket_id = 'brand-logos'
    and exists (
      select 1 from public.brands b
      where b.id::text = (storage.foldername(objects.name))[1]
    )
  );
```

```js
#!/usr/bin/env node
/**
 * Fails when `supabase/config.toml` still carries the local-only auth
 * settings and something is about to push it at a hosted project.
 *
 * `enable_signup = true` with `enable_confirmations = false` is correct for
 * the local stack — it is what lets integration tests sign in with a
 * password. The CLI pushes this file verbatim, so on a hosted project the
 * same two lines let anyone self-register an arbitrary address,
 * pre-confirmed, against a product whose stated auth surface is magic link
 * and Google.
 *
 * Opt in with DEPLOY_TARGET=hosted. Local runs are unaffected, which is the
 * point: the local settings are not a mistake, deploying them is.
 */
import { readFileSync } from "node:fs";

if (process.env.DEPLOY_TARGET !== "hosted") {
  console.log("check-deploy-config: DEPLOY_TARGET is not 'hosted' — skipping.");
  process.exit(0);
}

const config = readFileSync("supabase/config.toml", "utf8");
const problems = [];

if (/^\s*enable_signup\s*=\s*true/m.test(config)) {
  problems.push("enable_signup = true — anyone could self-register on a hosted project.");
}
if (/^\s*enable_confirmations\s*=\s*false/m.test(config)) {
  problems.push("enable_confirmations = false — registrations would be pre-confirmed.");
}

if (problems.length > 0) {
  console.error("supabase/config.toml is not safe to push to a hosted project:\n");
  for (const problem of problems) console.error(`  - ${problem}`);
  console.error("\nSee docs/DEPLOY-CHECKLIST.md.");
  process.exit(1);
}

console.log("check-deploy-config: config.toml is safe for a hosted target.");
```

## Explicitly NOT in this plan

Each of these was considered and deferred. None is an oversight.

- **A `legacy_id` column for import idempotency.** Re-importing the same pre-Postgres backup still duplicates records whose ids were remapped. The fix is a nullable per-org `legacy_id` with a per-org unique index on four tables; deferred to Phase 4, which touches the same tables for DPDP erasure. Deterministic remapping is not an alternative — `email_templates.id` is a global primary key, so hashing a legacy id to a fixed uuid makes two accounts importing the same backup collide.
- **Dropping `brands.logo_data`.** Needs either a backfill of every remaining base64 logo into Storage, or accepting that those logos disappear. Neither has been decided, and both need the hosted project that does not exist yet.
- **Deleting Storage objects.** Deliberate. An old object may be the one an issued invoice's frozen `brand_snapshot` still references, so deleting on brand delete or on re-upload breaks rendering a PDF for an invoice issued while it was current.
- **Making import all-or-nothing.** Conflict resolution spans interactive dialog round-trips, so no transaction can cover it. Per-record accounting is the deliberate alternative — an import that is atomic only when it happens not to collide is a worse contract than one that is never atomic and always accurate.
- **A per-account data cap.** A product decision, not a bug fix.
- **Sentry, and wiring `proxy.ts`'s `getClaims()` catch to it.** Sentry is out of scope until the landing-page phase (spec §12).
- **The landing page, SEO, `/pricing`, `/privacy`, `/terms`.** `PUBLIC_PATHS` already routes the last three; the marketing and legal-gate phases add them.
- **Turning on `FEATURES.billing` or `FEATURES.followups`.** No payment provider and no email provider are wired. Both flags stay `false`.
- **A two-browser concurrency test.** `src/test/integration/rpc.test.ts` fires concurrent RPCs from one client, which exercises the lock. The end-to-end two-tab path needs a browser harness this project does not have.
- **`site-header.tsx` showing "New client" while editing.** Locked by a test transcribed from the design handoff's breadcrumb table, so fixing it means amending that spec row too.
- **`defaultFollowupConfig`'s hardcoded `templateId`, and `CURRENCY_ORDER`'s duplication.** Both degrade quietly and neither is reachable while `FEATURES.followups` is off.
- **A copy pass on `login/page.tsx`'s raw Supabase error strings.** `toast(error.message)` surfaces provider text in an app whose copy is otherwise hand-written, dry and second-person. It belongs with the landing page's copy pass, not on its own.
